# 메멘토모리: 제품 판단과 실행 계획

> 이 문서의 초기 플랫폼 검토와 MVP 범위는 개발 당시 기록입니다. 현재 구현 상태는 [플랫폼 기준](PLATFORMS.md), 후속 목표·행동 기능의 상세 기획은 [새 PRD](PRD-mementomori-life-goals.md), 개발 순서는 [구현 계획](IMPLEMENTATION-life-goals.md)을 따릅니다. 아래의 초기 ‘할 일 기능 제외’ 결정은 후속 PRD 범위에서 재검토됐으며, 목표·행동 기능은 아직 구현하지 않았습니다.

## 디자인 업데이트 · 2026-09-26

사용자 피드백에 따라 모노톤 + Pretendard로 변경했다. [29CM UI 아카이브](https://wwit.design/2021/03/31/29cm/)의 선명한 대비, 타이포그래피와 단순한 구획을 참고했다. 우선 OS·플랫폼 선택과 네이티브 확장은 디자인 개선 후 다시 논의한다. 아래 플랫폼 항목은 기존 검토안이며 확정 일정이 아니다.

## 핵심 판단

‘삶이 유한하다는 것을 일상에서 느끼게 한다’는 가치가 분명하다. 초가 실제로 줄어드는 화면은 설명보다 빠르게 이를 전달할 수 있다. 다만 카운트다운을 한 번 보는 감동과 오래 곁에 두는 가치는 별도로 검증해야 한다. 첫 버전의 목적은 **짧게 바라본 시간이 오늘의 선택을 바꾸는지** 알아보는 것이다.

제품의 한 문장: **언젠가 끝나기에, 지금이 소중합니다.**

평가는 시장 조사 결과가 아닌 현재 아이디어에 대한 제품 판단이다.

| 항목 | 평가 | 제품에 반영할 판단 |
| --- | --- | --- |
| 가치 전달 | 강함 | 첫 화면에서 줄어드는 시간을 즉시 보여준다. |
| 진입 부담 | 낮출 수 있음 | 가입 없이 생년월일 하나로 시작한다. |
| 지속 사용 | 아직 미검증 | 앱을 찾아오는 것보다 일상에 놓이는 표면을 우선한다. |
| 차별성 | 숫자만으로는 약함 | 차분한 시각 언어, 작은 상시 표시 창, 오늘의 한 문장으로 경험을 완성한다. |
| 구현 비용 | 웹은 낮음, 기기별 위젯은 높아짐 | 웹으로 감각과 사용성을 검증하고 우선 기기의 위젯 한 종류를 만든다. |
| 수익성 | 아직 판단하기 이름 | 알림·유료화보다 사용자가 자발적으로 곁에 두는지 먼저 검증한다. |

## 가장 중요한 제품 결정

### 1. 통계의 정밀함과 개인 예측을 구분한다

기본값은 대한민국 2024년 생명표의 출생 시 기대수명 83.7년이다. 이는 이미 성인이 된 사람의 현재 나이에 조건부로 주어지는 기대여명과 다르다. ‘당신이 죽을 때까지’ 또는 ‘예상 사망일’이라는 표현은 쓰지 않는다. 화면에는 ‘기준 수명까지 남은 시간’으로 표시한다.

초 단위 숫자는 **흐름을 감각적으로 보여주는 표현**이다. 사용자 개인의 남은 수명을 초 단위로 안다는 뜻이 아니다. 첫 버전은 요청의 단순함을 살려 전체 평균을 사용하고, 성별·건강 설문은 받지 않는다. 기준 수명은 직접 바꿀 수 있다. 기준을 넘겨도 음수나 실패 상태로 표현하지 않는다.

후속으로 통계적 타당성이 더 중요해지면 연령별 기대여명을 검토한다. 그때도 매일 목표 날짜를 뒤로 미루는 모델은 카운트다운의 의미를 바꾸므로, 설정 시점에 기준을 고정하는 정책이 필요하다.

### 2. 죽음에 대한 자각에서 오늘의 선택으로 이어진다

카운트다운만 있으면 사용자가 익숙해지거나 압박만 느낄 가능성이 있다. 이는 검증할 가설이다. ‘오늘 무엇을 아끼고 싶은가’라는 짧은 질문 하나를 곁에 둔다. 기록은 선택 사항이며, 할 일 목록·연속 기록·완료 점수로 확장하지 않는다.

### 3. 오래 붙잡는 앱이 아니라 자주 눈에 닿는 도구다

체류시간을 성공 지표로 삼지 않는다. 몇 초 보고 일상으로 돌아가는 사용이 가치일 수 있다. 작은 창, 홈 화면 위젯, 워치의 시계 화면 등으로 확장하되 모든 플랫폼을 동시에 만들지 않는다.

## 첫 버전 범위

구현 완료한 범위:

- 생년월일과 기준 수명 입력. 처음에는 예시임을 명확히 표시한다.
- 현재 시각을 기준으로 매초 갱신하는 카운트다운, 일 단위 모드.
- 지나온 삶의 비율, 한 점이 한 주인 달력.
- 오늘 아끼고 싶은 한 문장. 기기 현지 날짜가 바뀌면 새로 시작한다.
- 노트북 Chrome의 Document Picture-in-Picture 작은 창.
- 집중 화면, 모바일 반응형 화면, PWA 설치 정보.
- 최초 온라인 준비 후 오프라인 실행.
- 기기 내 저장, 다른 탭과 설정 동기화, 기록 삭제.

첫 버전에 넣지 않은 기능:

- 실제 iOS/Android 홈 화면 위젯, 스마트워치 앱.
- 계정, 기기 간 동기화, 서버, 외부 분석 SDK.
- 알림, SNS 공유, 건강 기반 개인 수명 예측, 결제.

## 기술 선택

**Vite + JavaScript + CSS + localStorage + Service Worker**를 선택했다. 애플리케이션의 상태가 작고 서버 데이터가 없으므로 React/Next.js와 데이터베이스를 추가할 이유가 아직 없다. 폰트도 함께 배포하여 사용 시 외부 폰트 서버를 호출하지 않는다.

| 표면 | 현재 범위 | 한계 / 다음 판단 |
| --- | --- | --- |
| 노트북 웹 | 구현 | 탭이 보일 때 매초 갱신. 잠자기 후 현재 시각으로 복구. |
| 노트북 작은 창 | 구현 | 지원되는 데스크톱 Chrome 환경. 원래 탭 종료 시 창도 닫힘. OS 상주 앱은 아님. |
| 휴대폰 PWA | 구현 | 설치 아이콘과 독립 창. 홈 화면 위젯 또는 잠금 화면 위젯과는 다름. |
| iPhone 위젯 | 후속 | SwiftUI + WidgetKit. 시스템의 동적 날짜 표시 활용을 검토. 임의의 총 초 숫자를 매초 업데이트하는 방식은 보장하지 않음. |
| Apple Watch | 후속 | WidgetKit/complication을 기기에서 검증. Always-On에서 초 단위 갱신을 약속하지 않음. |
| Android 위젯 | 후속 | 네이티브 위젯 필요. 일반 주기 갱신은 30분 미만을 지원하지 않음. 시간용 시스템 컴포넌트로 표현 가능한 형식을 별도 검증. |

따라서 **모든 기기에서 동일한 총 초 숫자를 항상 갱신**하는 약속은 하지 않는다. 가치를 유지하는 방향은 ‘위젯에는 삶의 주·일과 한 문장, 앱을 열면 초 단위 흐름’이다. Apple의 동적 타이머는 별도 실기기 실험을 통해 가능한 범위를 넓힌다.

계산 규칙: `기준 시각 = 생년월일 현지 자정 + 기준 수명 × 365.2425일`. `남은 초 = max(0, ceil((기준 시각 − Date.now()) / 1000))`. 간격 타이머는 화면 갱신에만 쓰며, 초를 누적 차감하지 않는다. 시간대 변경 시 생일의 현지 자정도 달라질 수 있다. 데이터 버전은 v1이며 기기 사이의 동일한 절대 목표 시각은 보장하지 않는다.

## 다음 실행 순서

### 지금: 직접 3일 사용

실제 생일을 설정하고 노트북 작은 창을 곁에 둔다. 차분한 정서를 기본 가정으로 만들었으므로 사용자가 원한다면 강도·색·문구를 조정한다. 우선 확인할 것은 숫자가 주는 감각, 보고 싶은 빈도, 실제로 곁에 두는 위치다.

### 다음: 5명에게 7일간 사용 요청

테스트 사용자는 ‘평소 시간을 무심코 흘려보낸다고 느끼고, 자기 성찰 도구를 자발적으로 찾는 사람’을 가정한다. 타깃은 사용자 확인 후 좁힌다. 개인정보나 생년월일을 수집하지 않고 인터뷰로 검증한다.

아래 기준은 성공이 증명된 벤치마크가 아니라, 미리 정하는 작은 실험의 판단선이다.

- 5명 중 4명 이상이 설명 없이 1분 안에 자신의 시간을 설정한다.
- 5명 중 3명 이상이 7일째에도 작은 창이나 바로가기를 유지한다.
- 5명 중 3명 이상이 ‘서비스를 보고 오늘 실제로 바꾼 선택’ 한 가지를 구체적으로 말한다.
- 가치를 느끼지 못했거나 사용을 꺼리게 된 이유도 함께 기록한다.

핵심 질문은 ‘좋았나요?’가 아니라 ‘마지막으로 이 화면을 본 뒤 무엇을 다르게 했나요?’다. 만족도만으로 네이티브 앱 개발을 결정하지 않는다.

### 검증 후: 가장 많이 쓰는 표면 하나를 네이티브로

iPhone 수요가 가장 크면 SwiftUI + WidgetKit부터 구현한다. 먼저 **수십 년짜리 기간이 위젯에서 어떻게 표시되는지, 화면이 꺼져 있거나 Always-On일 때 갱신이 어떻게 제한되는지** 작은 기술 실험으로 확인한다. 표현이 적합하면 iOS 위젯을 배포하고 워치로 확장한다. 노트북 수요가 우세하면 새 탭 확장 또는 메뉴 막대 앱을 먼저 검토한다.

계정과 동기화는 여러 기기에서 같은 설정을 쓰고 싶다는 반복 요청이 생긴 뒤 추가한다. 초기 가격 실험은 고급 테마나 위젯 꾸미기 같은 선택 기능의 일회성 구매부터 검토할 수 있으나, 아직 결제 구현은 하지 않는다.

## 2026-09-26 플랫폼 결정

사용자 승인: 웹 + macOS 독립 작은 창 앱을 함께 구현한다. 첫 Mac 버전은 SwiftUI/AppKit, 로컬 저장, 서버 없는 구조다. 기존 세 가지 위젯 디자인을 재현하고 일반 창 위에 표시한다. 웹과 Mac은 버전이 있는 JSON 설정 파일로 수동 이동하고 공통 계산 fixture로 동등성을 확인한다. 모바일 위젯, 로그인·클라우드 동기화, 자동 업데이트, 로그인 시 자동 실행은 이번 구현 범위에서 제외한다. 앱 서명·공증은 공개 배포 단계에서 진행한다. 기존 문서의 ‘플랫폼 미정’ 내용은 이 결정으로 대체한다.
